The setup

Three era configs run the same task against the same deterministic scripted worker (public/model.mjs). Nothing about the model changes — the only variable is the control surface each config exposes. That is the article's claim made executable: at every era, the outcome difference comes from the lever, not the intelligence.

The task

Prepare the v2.4 release. Ground truth (public/pool.mjs):

  • changelogFormatted — the entry must follow changelog-spec, reachable only if the spec survives into the window.
  • versionBumped — VERSION must become 2.4.0, reachable only through the edit-file tool.
  • checksGreen — run-checks must actually run and pass, which needs both VERSION and the release channel fixed — a loop with a reason to continue.

The three control planes

  • Era 1 — the words. Fixed-order admission: docs enter in pool order, the first overflow cuts it and everything after. An irrelevant doc eats the budget; the spec is scissored. No tools, one turn, no verifier.
  • Era 2 — what goes in. Curated admission inside a budget; every selected doc is charged on every turn. Tools exist and results return as raw history — but nobody engineered the stop, so the worker declares done on its own say-so.
  • Era 3 — the loop. Same window and tools, plus a verifier (checks.lastResult === "pass"), an attempt-log memory that decides what survives between turns, and a turn budget. Termination is engineered, not felt.

Try it

  • npm start — this UI on :3000.
  • npm run report — the CLI side-by-side.
  • node scripts/report.mjs examples/configs/era-2-tight-budget.json — watch curation fail when the budget can't hold the spec.
  • Edit a config in examples/configs/ and re-run — validateConfig enforces the budget as a hard wall.

Zero dependencies · the model is scripted on purpose — the lever is the variable, not the intelligence.
